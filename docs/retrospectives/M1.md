**Deviations from the guide:**

1. **B.3.7 schema extension: `allow_self_registration` field.**
   The guide's B.3.7 model spec doesn't list this field. We added
   it as a per-provider policy hook for B.4.6 step 4 ("create a
   global User only if platform policy allows external self-
   registration"). Default is False (invitation-only). Tracked
   because future M1+ work that touches B.3.7 should preserve this
   field, and any guide update should fold it into the spec.

2. **B.4.7 rule #5 NOT enforced inside `resolve_external_user`.**
   B.4.7 rule #5 says silent linking is allowed only if "user is
   completing an invite flow or passes a local confirmation
   challenge." This is a UI state-machine rule that crosses HTTP
   boundaries; the service can't know whether the calling context
   is an invite flow. We enforce rules 1-4 strictly via
   `require_verified_email=True` + the conflicting-identity check.
   Rule #5 lives one level up in the adapter / invite-acceptance
   view. **The `LinkingNotAllowedError` exception is defined but
   not raised in M1 D5**; the invite flow lands in a later
   milestone.

3. **J.3.9 #6 — "OAuth login works through configured test
   provider" verified at the adapter boundary, not via a full HTTP
   integration test with a mock OIDC issuer.** Original Phase 6
   plan included a mock OIDC issuer fixture (~200 lines) using
   `responses` to intercept allauth's network calls; switched to
   service+adapter depth after weighing test value vs. fixture
   complexity. The adapter-boundary test exercises the same code
   paths that an HTTP integration test would (resolution, audit
   emission, sociallogin.user mutation). Cryptographic validations
   (state, nonce, signature) live in allauth's pipeline; M8
   production-readiness verification (J.10.3) covers them with a
   real provider.

4. **Trusted-provider TOTP-challenge bypass NOT implemented.**
   B.4.8 says provider MFA "MAY satisfy" login MFA. Our middleware
   bypasses *enrollment* for trusted-provider users but the
   *TOTP challenge* (allauth.mfa's own middleware) still fires if
   the user has previously enrolled TOTP. Disabling that challenge
   for trusted-provider users would require disabling allauth's
   challenge middleware conditionally — a much larger change.
   Conservatively safe: the trusted-provider user sees an extra
   challenge, not a security regression. Tracked for a future
   polish PR.

5. **`SOCIALACCOUNT_PROVIDERS` loaded via `post_migrate`, not
   `ready()`.** Django emits a `RuntimeWarning: Accessing the
   database during app initialization is discouraged` when
   `AppConfig.ready()` does DB work. We moved the loader call to
   the `post_migrate` signal, which fires after migrations
   (including test-DB setup). Tradeoff: a long-running web server
   that adds a `OAuthProviderConfig` row at runtime (via shell or
   admin) won't see it until next deploy. Acceptable for M1 D5;
   future polish: `manage.py reload_oauth_providers` command.

6. **OAuth signal handler for cancellation NOT wired.** Allauth
   doesn't emit a dedicated signal for "user clicked cancel at
   provider" that carries enough context for a structured audit
   event. The `socialaccount/login_cancelled.html` template handles
   the user-facing path; no `OAUTH_LOGIN_FAILED` with
   `failure_reason='user_cancelled'` is emitted. Tracked.

7. **`social_account_login_failed` signal availability is
   version-conditional.** Wired with an `ImportError` fallback that
   logs a warning. If a future allauth version moves the signal,
   the import fallback fires and only that one audit path is
   degraded.

**Audit event catalog additions (M1 D5):**

The following B.4.19 codes are emitted in M1 D5 (in addition to the
M1 D4 catalog):

* `OAUTH_LOGIN_STARTED` — emitted from adapter on every
  `pre_social_login`.
* `OAUTH_LOGIN_SUCCEEDED` — emitted from
  `social_account_added` (first link) and `social_account_updated`
  (repeat login) signal handlers.
* `OAUTH_LOGIN_FAILED` — emitted from adapter on typed exception,
  with `failure_reason` metadata: `provider_not_active`,
  `domain_not_allowed`, `email_not_verified`, `conflicting_identity`,
  `user_inactive`, `no_existing_user`, `authentication_error`
  (from `social_account_login_failed` signal handler).
* `OAUTH_ACCOUNT_LINKED` — emitted from `resolve_external_user`
  service (Phase 2).
* `OAUTH_ACCOUNT_UNLINKED` — emitted from `social_account_removed`
  signal handler.
* `OAUTH_PROVIDER_MFA_TRUSTED` — emitted from middleware (Phase 4)
  once per session for trusted-provider users.
* `OAUTH_PROVIDER_MFA_NOT_TRUSTED` — emitted from middleware
  (Phase 4) once per session for untrusted-provider users.
