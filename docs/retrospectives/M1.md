## What shipped

### Phase 1 — Foundation

- New app `apps.platform.console` at URL prefix `/platform/`.
- `PlatformConsoleAccessMixin` enforces `is_staff` via dispatch
  hook. Anonymous → redirect to login; authenticated non-staff →
  `PermissionDenied` (403, not 302).
- Helper `apps/platform/accounts/utils/email_verification.py`
  with `ensure_verified_email_address(user)` — idempotent
  upsert that powers BOTH the seed-dev-tenant command and the
  `createsuperuser` ergonomics fix.
- `UserManager.create_superuser` extended to call the helper
  after the user is created. The "first-time admin can't log
  in because allauth requires email verification" footgun is now
  fixed.
- Skeleton views in place for orgs, users, signing keys,
  impersonation — placeholder pages each pointing at their
  target phase.

**Deviation:** chose approach (c) — extend `UserManager.create_superuser`
— over approach (a) — write a separate management command.
The deviation note is captured here rather than in handoff.md
because it's an internal implementation choice with no
operator-visible difference.

### Phase 2 — Read-only org/user surfaces

- `OrgListView` with `?q=` search on name/slug, paginated 25/page.
  Annotates `active_member_count` via `Count(filter=Q(...))` to
  avoid N+1.
- `OrgDetailView` shows org metadata + member roster.
- `UserSearchView` — search-driven (no query → no results) to
  avoid scanning the user table.
- `UserDetailView` shows email, MFA status (boolean only, never
  the secret), security counters, memberships.
- Templates use the `mph-settings-card` chrome class for visual
  consistency.
- Template context uses `subject_user` (not `user`) to avoid
  shadowing Django's auto-populated `request.user` in templates.

**Confirmed behavior:** `TenantManager` does NOT auto-filter
querysets per the M1 D6 docstring; the platform console reads
across orgs using the default manager. No bypass mechanism
needed. The B.1.7 isolation guardrail is a CI-level model-shape
check, NOT a runtime queryset filter.

### Phase 3 — Handoff signing key management UI

- `SigningKeysListView` lists all keys with computed lifecycle
  state (pending / primary / active overlap / retired) and
  state-appropriate action affordances.
- `SigningKeyCreateView`, `SigningKeyPromoteView`,
  `SigningKeyRetireView`, `SigningKeyEmergencyRotateView`.
- All state-changing endpoints use the two-page confirmation
  pattern: GET shows confirmation, POST performs. CSRF-protected
  by standard Django middleware (root domain).
- Actor for service calls is `request.user.id` (the staff admin),
  NOT the system user.
- Service exceptions are caught and rendered inline on the
  confirmation page rather than escaping as 500s.

**URL design.** Emergency rotate is at
`/platform/signing-keys/emergency-rotate/` with NO key_id URL
parameter. The service signature is
`emergency_rotate_handoff_signing_key(*, actor_id, new_key_id)` —
the service determines the current primary itself via
`active_handoff_signing_keys_ordered_by_created_desc()[0]`. The
operator types the NEW key id on the confirmation form.

### Phase 4 — Impersonation backend

- `apps.platform.accounts.impersonation` subpackage with its own
  models, services, exceptions. Mirrors the `oauth/` and
  `handoff/` precedent.
- `ImpersonationSession` model (UUID v7 primary key, all FKs
  `PROTECT`). Cross-field invariants enforced at the DB level:
  - `admin_user != target_user` (CHECK).
  - `ended_at >= started_at` when set (CHECK).
  - `ended_at` and `ended_by_user` set together or both null
    (CHECK).
  - Partial unique index: at most one active session per admin.
- `ImpersonationEndReason` TextChoices: `ADMIN_ENDED`,
  `LOGOUT`, `EXPIRED`.
- Service `start_impersonation`:
  - Keyword-only primitive args.
  - Validation order: self-target check, reason length (>=10),
    actor staff+active, target exists/active/not-system/not-staff,
    membership matches+ACTIVE, no existing active session.
  - Each validation failure audits `IMPERSONATION_DENIED` with
    a reason code BEFORE raising the typed exception.
  - Race-window handling: if the partial unique index rejects
    a concurrent insert, the `IntegrityError` is caught, the
    outer atomic rolls back, then `_audit_denied` runs in a
    fresh atomic block.
- Service `end_impersonation`:
  - `SELECT FOR UPDATE` on the session row serializes concurrent
    end calls.
  - Validates `end_reason` against `ImpersonationEndReason.choices`.
  - Audit metadata includes admin/target ids and
    `duration_seconds`.

**Strict v1 interpretation of B.7:** no staff-on-staff
impersonation, no system-user impersonation. Trade-off
captured below.

**Audit codes added:** `IMPERSONATION_STARTED`,
`IMPERSONATION_ENDED`, `IMPERSONATION_DENIED`. Registered in
`_KNOWN_EVENT_TYPES`. To be folded into G.5.2 in M2.

### Phase 5 — Impersonation UI + tenant integration

Backend integration with the handoff flow:

- `HandoffResult` gains `impersonator_admin_id: UUID | None`.
- `issue_handoff_token` gains optional `impersonator_admin_id`
  parameter; cross-field invariant enforces
  `impersonator_admin_id set ⇔ auth_method == "impersonation"`.
- JWT carries optional `iai` claim ("impersonating admin id").
  Absent for non-impersonation tokens — old verification still
  works.
- `consume_handoff_token` reads `iai` into HandoffResult.
- `establish_tenant_session` writes new session key
  `mph_session_impersonator_admin_id` (None for non-impersonation
  so every session has the same shape).
- `TENANT_SESSION_ESTABLISHED` audit metadata includes
  `impersonator_admin_id` when present.

UI surfaces:

- `UserImpersonateView` at `/platform/users/<uuid>/impersonate/`.
  GET shows confirmation form (membership picker + reason);
  POST calls `start_impersonation`, mints an impersonation
  handoff token, renders auto-POST form to tenant subdomain.
  Uses its own template `impersonate_handoff_redirect.html`
  rather than reusing `auth_portal/handoff_form.html` (the
  contexts are conceptually distinct).
- `ImpersonationLogView` replaces the Phase 1 placeholder.
  Lists active sessions (with end action) and 50 most-recent
  ended sessions.
- `EndImpersonationFromConsoleView` at
  `/platform/impersonation/<uuid>/end/`.
- Tenant-side `EnforceImpersonationLiveness` middleware. Runs
  on EVERY tenant request. Short-circuits to no-op when the
  session has no `mph_session_impersonator_admin_id`. When the
  session IS an impersonation, checks the
  `ImpersonationSession.objects.active_for_admin(...)` row; if
  no active session (ended out-of-band from console), force
  `django.contrib.auth.logout` and redirect to root picker.
- Tenant landing template gains the yellow/orange impersonation
  banner with admin email and "End impersonation" button.
- `EndImpersonationFromTenantView` at `/end-impersonation/`
  (tenant URL). Ends with `end_reason=ADMIN_ENDED`, flushes
  tenant session, redirects to root.
- `TenantLogoutView` now ends impersonation with
  `end_reason=LOGOUT` before flushing the session.

## Deviations from the guide / spec

### Strict v1 interpretation of B.7

- **No staff-on-staff impersonation.** B.7 doesn't explicitly say
  staff users can be targets. The strict reading is that admin A
  impersonating admin B would inherit admin B's platform-console
  access, which is a real security concern. The service raises
  `ImpersonationTargetInvalidError` with reason code
  `target_is_staff`.

  **Trade-off:** legitimate "senior admin investigating another
  admin's session" use case is not possible. Mitigation: audit
  log review. If this becomes painful, a future iteration could
  add a `--allow-staff-target` flag with elevated approval.

- **No system-user impersonation.** Impersonating the system user
  makes no semantic sense (it's a singleton sentinel). Service
  raises with reason code `target_is_system`.

- **No staff-on-staff via senior end.** Phase 4's
  `end_impersonation` permits any staff user to end any session,
  including someone else's. This is by design — a senior admin
  must be able to end a runaway impersonation.

### Minimum reason length

`start_impersonation` requires a reason of at least 10
characters (post-strip). B.7 says only that a reason must be
recorded. The 10-char floor is to discourage "test", "x", "asdf"
placeholders that wouldn't help audit reconstruction months
later. Tracked here in case operators report friction.

### Emergency rotate URL design

The emergency rotate confirmation page takes a `new_key_id`
form field rather than auto-generating one. Rationale: matches
the discipline of the create flow (operator names their keys
explicitly); auto-generation with a timestamp could collide if
rotation runs twice in the same second. Operators in an
emergency are presumed competent.

### EnforceImpersonationLiveness middleware doesn't audit

The middleware force-logs-out tenant sessions when the
underlying `ImpersonationSession` row has been ended elsewhere.
It does NOT emit `TENANT_SESSION_LOGOUT` for that flush. The
rationale: `IMPERSONATION_ENDED` (emitted by the
`end_impersonation` service in the path that actually closed
the row) captures the meaningful event. The middleware-driven
logout is mechanical cleanup. **Could be revisited in M2** if
auditors find the missing event makes timeline reconstruction
harder.

### `createsuperuser` ergonomics — approach (c)

Chose approach (c) — extend `UserManager.create_superuser` —
over approach (a) (separate management command). Reason: the
shared utility powers BOTH the seed_dev_tenant command and the
createsuperuser path. The User model layer is a slightly
unusual home for an `EmailAddress` upsert (allauth's
`EmailAddress` is conceptually separate from User), but the
inline import + utility call keeps the coupling soft. The
seed_dev_tenant `Command._ensure_verified_email_address` wraps
the utility and returns the tuple shape its caller expects.

## Recurring failure modes (the big lesson)

This milestone got bitten THREE TIMES by the same root pattern.
Naming it explicitly so future milestones don't repeat:

> **Producing changes to files I haven't seen.**

Three concrete instances:

1. **Phase 1 → seed_dev_tenant fix.** I refactored
   `_ensure_verified_email_address` from a method to a function
   without `self`. The call site passes `user=user` as a kwarg.
   Python bound `self` to the first positional arg, then got a
   second `user` from the kwarg → `TypeError: got multiple
   values`. **Four test failures.**

2. **Phase 3 → emergency rotate signature.** I guessed
   `emergency_rotate_handoff_signing_key(*, actor_id,
   current_primary_key_id)`. Actual signature: `(*, actor_id,
   new_key_id)`. Caught at the planning step by stopping to
   read `_keys.py`, but only AFTER drafting half the templates
   and tests based on the wrong signature.

3. **Phase 5 → `client.force_login` + manual session writes.**
   I built tenant-side tests assuming `client.force_login`
   would work for tenant subdomain requests. `PerTenantSessionMiddleware`
   uses host-derived cookie names; `force_login` writes the
   ROOT cookie name; tenant requests don't see the session.
   Missed `MPH_HOST_URLCONF_ROUTING_ENABLED` autouse fixture
   entirely. **5+ failures across two rounds of patching.**

### What I changed mid-milestone

After incident #2, I committed to "request file contents before
producing changes to files I haven't seen." This caught
incident #3's planning errors but not its execution errors
(I still wrote tests against the subsystem without reading the
existing test pattern).

After incident #3, the commitment expanded to:

> **Before producing changes to a subsystem, request both the
> source file AND the closest existing test file for that
> subsystem.**

The "closest existing test file" clause matters because tests
encode operational knowledge (autouse fixtures, helper
patterns, host-cookie quirks) that docstrings don't.

### Related: fixture name semantics

Phase 5's final round hit a secondary version of the same
pattern: **assuming a fixture name implies its behavior.** The
`user_verified_with_totp` fixture has email
`verified-nomfa@example.test` — the name is misleading. The
working fixture is `user_with_totp`. I used the wrong fixture
in three test files because I trusted the name over the source.

**Fixture naming bug in the codebase:** `user_verified_with_totp`
should be renamed or its docstring corrected. Track for a
cleanup pass.

## Real product gaps surfaced (track for M2 / later)

These are not Phase 5 bugs but real gaps the work uncovered:

1. **Impersonating a no-TOTP target lands them on the TOTP
   enrollment page.** `RequireMfaEnrollmentMiddleware` fires
   on every tenant request where the authenticated user has
   no TOTP. After impersonation handoff, `request.user` IS the
   target. If they have no TOTP, the middleware redirects.

   **Mitigation options:**
   - (a) Middleware bypasses enrollment when session has
     `impersonator_admin_id` set. Cleanest. The admin's MFA
     already gated start.
   - (b) `UserImpersonateView` refuses if target has no TOTP.
     Stricter but limits utility for "user can't log in, needs
     help" scenarios — which is exactly when impersonation is
     most useful.
   - (c) Document the limitation; operators work around it.

   **Recommendation: (a)** in M2 alongside the audit work,
   since the middleware ALREADY reads the session.

2. **MFA middleware redirect URL is root-relative on tenant
   subdomain.** The middleware sets `Location:
   /accounts/2fa/totp/activate/` on tenant requests. The
   tenant urlconf doesn't have that path → 404 in browsers.
   Production bug if any tenant-side MFA gate is ever hit.
   **Track for M2.**

3. **EnforceImpersonationLiveness middleware runs ONE extra
   DB query per tenant request when impersonating.** Acceptable
   at current scale. If impersonation usage grows, consider
   caching the active-session lookup in the session itself
   (e.g. write `mph_session_impersonation_session_id` and only
   re-check on a heartbeat).

4. **Platform console URL space is flat.** All admin functions
   live directly under `/platform/`. As M2 RBAC, M2A
   entitlements, and later phases add admin functions, this
   will need grouping. **Not blocking, but worth a design
   pass at M2 start.**
